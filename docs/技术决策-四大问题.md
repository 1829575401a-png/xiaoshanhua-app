## 问题一：AI 语音评测技术选型

### 调研结论

| 方案 | 方言支持 | 自定义文本 | 评分维度 | 价格参考 | 结论 |
|------|---------|-----------|---------|---------|------|
| **腾讯云智聆（SOE）** | ❌ 仅中英文普通话 | ✅ 支持 | 准确度、流利度、完整度、重音、音素 | 免费额度 500次/天 | **不适用** |
| **讯飞语音评测（流式版）** | ❌ 仅普通话+英文 | ✅ 支持 | 准确度、流利度、完整度 | 按调用量计费 | **不适用** |
| **百度语音评测** | ❌ 仅中英文 | ✅ 支持 | — | — | **不适用** |

> ⚠️ **关键发现**：目前市场上所有主流第三方语音评测 API（腾讯云、讯飞、百度）均**不支持吴语或任何中文方言**的发音评测。它们仅支持标准普通话和英文。

### 决策建议

**推荐方案：自研轻量级评分引擎 + 普通话模型兜底**

由于第三方 API 都不支持方言评测，我们需要自研方案。考虑到 MVP 阶段的资源约束，建议采用**渐进式策略**：

| 阶段 | 方案 | 说明 |
|------|------|------|
| **MVP（2个月内）** | 方案 A：基于声学特征的规则评分 | 轻量级，无需训练数据 |
| **V1.1（3-4个月）** | 方案 B：开源模型微调 + 小样本训练 | 准确率提升，需要标注数据 |
| **V2.0（6个月+）** | 方案 C：自研专用模型 | 高准确率，需要大量语料 |

---

### 方案 A 详解：基于声学特征的规则评分（MVP 首选）

**原理**：提取用户录音和标准发音的声学特征，计算相似度后映射为 0-100 分。

**技术路径**：

```
用户录音（mp3）          标准发音（mp3）
      │                      │
      ▼                      ▼
  提取 MFCC 特征         提取 MFCC 特征
  （13维梅尔频率          （预计算并存储）
   倒谱系数）                │
      │                      │
      ▼                      ▼
  ┌──────────────────────────┐
  │  DTW 动态时间规整算法    │  ← 对齐两段音频的时间轴
  │  计算特征序列相似度      │
  └──────────┬───────────────┘
             │
             ▼
  ┌──────────────────────────┐
  │  相似度 → 分数映射       │  ← 余弦相似度 × 100
  │  + 薄弱音节检测          │  ← 逐帧分析，标注偏差大的段落
  └──────────┬───────────────┘
             │
             ▼
       评分结果（0-100）+ 薄弱音节
```

**所需技术栈**（Python 后端）：

| 组件 | 推荐库 | 用途 |
|------|--------|------|
| 音频处理 | `librosa` | 加载音频、提取 MFCC 特征 |
| 时序对齐 | `fastdtw` 或 `dtw-python` | DTW 算法对齐两段音频 |
| 相似度计算 | `numpy` / `scipy` | 余弦相似度计算 |
| API 服务 | `FastAPI` | 封装为 REST API |

**优势**：
- 零训练数据需求，有标准音频即可
- 开发周期短（约 1-2 周可完成原型）
- 不依赖外部 API，无调用成本
- 完全离线可运行

**劣势**：
- 准确率不如深度学习方案（预估与人工评分一致性 60-70%）
- 无法识别"具体哪个音素错了"，只能标注"哪个时间段偏差大"
- 对背景噪音敏感

**MVP 阶段可行性**：✅ **可行**，能满足"给出大致评分 + 标注薄弱位置"的核心需求。

---

### 方案 B 详解：开源模型微调（V1.1 升级路径）

如果 MVP 验证通过且收集了足够用户录音数据（>1000 条标注数据），可以升级：

| 步骤 | 内容 |
|------|------|
| 1. 基座模型 | 使用 `wav2vec 2.0` 或 `HuBERT` 开源预训练模型 |
| 2. 微调数据 | 收集 500-1000 条人工评分的萧山话录音 |
| 3. 微调目标 | 在基座模型上加回归头，预测 0-100 发音得分 |
| 4. 部署 | 转换为 ONNX 格式，在云服务器上部署推理 |

**优势**：准确率可提升至 80-85%，能识别具体音素错误。

**劣势**：需要大量标注数据（MVP 阶段不具备），训练成本较高。

---

### 决策结论

> ✅ **MVP 采用方案 A（声学特征规则评分）**，在 PRD 的 AI 评分功能中实现。同时预留方案 B 的接口，确保后续可平滑升级。

## 问题二：微信小程序录音接口限制

### 调研结论

`RecorderManager.start()` 完整参数：

| 参数 | 可选值 | MVP 建议值 | 说明 |
|------|--------|-----------|------|
| `duration` | 最大 600,000ms（10分钟） | `15000`（15秒） | 一句方言通常 2-5 秒，15 秒足够 |
| `format` | `aac` / `mp3` / `wav` / `pcm` | **`mp3`** | 体积小、兼容性好、后端处理方便 |
| `sampleRate` | `8000` / `11025` / `12000` / `16000` / `22050` / `24000` / `32000` / `44100` / `48000` | **`16000`** | 语音识别标准采样率，平衡质量与体积 |
| `numberOfChannels` | `1` / `2` | `1`（单声道） | 语音评测仅需单声道 |
| `encodeBitRate` | 取决于采样率 | `48000` | 16kHz 采样率下的推荐码率 |
| `frameSize` | 单位 KB | `10` | 每 10KB 回调一次 `onFrameRecorded` |

### 关键能力确认

| 能力需求 | 是否支持 | 说明 |
|---------|---------|------|
| 最长录音 15 秒 | ✅ 支持 | `duration: 15000` |
| mp3 格式录音 | ✅ 支持 | `format: 'mp3'` |
| 16kHz 采样率 | ✅ 支持 | `sampleRate: 16000` |
| 录音后上传 | ✅ 支持 | 通过 `onStop` 回调获取 `tempFilePath`，上传至后端 |
| **实时音频流传输** | ⚠️ 不支持流式 | 小程序不提供实时音频流接口，只能录完再上传 |
| 帧数据回调 | ✅ 支持 | `onFrameRecorded` 可获取分帧数据，但不适用于流式传输 |

### 对 MVP 的影响

> ✅ **无阻断性影响**。我们的需求是"用户跟读一句 → 录音 → 上传 → 评分"，录音时长 2-5 秒 + 上传 1-2 秒 + 评分计算 1 秒，总延迟约 4-8 秒，在可接受范围内。

**注意**：
- 微信开发者工具**不支持录音测试**，必须在真机上调试
- iOS 和 Android 的录音行为有细微差异（格式兼容性），建议统一用 mp3
- 小程序进入后台时录音会自动暂停

### 决策结论

> ✅ **小程序录音接口完全满足 MVP 需求**，配置方案已确定。无需额外技术攻关。

## 问题四：萧山方言"标准音"选择

### 调研结论

根据《萧山市志》（2013）和吴语学堂的权威资料：

**萧山方言内部差异**：

| 区域 | 口音特点 | 代表方言地位 |
|------|---------|------------|
| **城厢（城区）** | 标准萧山话，受普通话影响适中 | ⭐⭐⭐⭐⭐ **代表方言** |
| 瓜沥/头蓬（东部） | 夹杂绍兴话成分 | ⭐⭐⭐ 亲属语言 |
| 临浦/楼塔（南部） | 夹杂诸暨话成分 | ⭐⭐⭐ 亲属语言 |
| 赭山/南阳（北部） | 夹杂海宁话因素 | ⭐⭐ 边缘变体 |
| 长河（西部，现属滨江区） | 曾被认为是典型萧山话 | ⭐⭐⭐⭐ 历史代表 |

**权威定论**：

> "代表萧山方言的是**城厢镇语言**" — 萧山政府网《萧山方言简介》

> 吴语学堂《萧山方言拼音方案》明确标注："反映以**萧山城区为代表的城厢口音**"。

### 决策结论

> ✅ **以萧山城厢口音为标准音**。发音人须为城厢出生且长期生活者。在课程介绍页注明"本课程采用萧山城厢口音"。未来可扩展其他区域口音作为补充课程。

**依据**：
1. 《萧山市志》和萧山政府网均认定城厢话为代表方言
2. 吴语学堂的萧山方言拼音方案基于城厢口音制定
3. 城厢是萧山政治文化中心，认同度最高
4. 萧山档案馆已收录城厢老派发音人的语音档案
